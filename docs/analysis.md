# Milestone 9: News intelligence (design for approval)

Status: **design, awaiting the owner's approval. No application code changes yet.**
Supersedes the earlier short proposal. Written 2026-11-23 from the owner's Milestone 9
specification, audited against the real data and the hardware.

**Principle:** turn every article into a structured, *evidence-checked* account of what
happened: what, who, when, where, why, how, impact, before, next, and what remains
unknown. Quality means accuracy and traceability, not fluent summaries.

---

## 0. Audit of the specification

**Adopted as written:**
- the 5W1H framing;
- facts, attributions, allegations, opinions and inferences kept distinct;
- conservative handling of missing information;
- one production model, chosen by measurement on our own articles;
- geographic resolution separate from the LLM, with coordinates never generated by the model;
- versioned, reproducible analyses;
- local-only inference;
- human evaluation;
- staged delivery.

**Changed, with reasons:**

| # | Specification | Problem | Design decision |
| --- | --- | --- | --- |
| 1 | One very large analysis per article (11 sections plus claims with quotes) | A 9B local model producing about 2–3k output tokens per article is slow and degrades JSON reliability. At an *estimated* 20–30 tokens/s that is 1–2 min per article, or **30–75 hours** for 1,820 articles. Not yet measured. | **Measure first (9.0).** Schema v1 is split into a **core pass** (overview, what, who, when, where, claims) and an **extended pass** (why, how, impact, context, next, open questions, tone). If measurements allow, both run in one call. |
| 2 | A "supporting quotation" for every claim | LLMs fabricate quotes, and the spec has no way to catch that | The article is sent as **numbered paragraphs**. Each claim cites a paragraph and a short verbatim quote. **Code verifies** the quote appears in that paragraph (after normalizing whitespace and quotation marks). Unverified claims are kept but flagged `evidence: unverified` and excluded from facts. |
| 3 | "Confidence" per claim | A model's self-reported confidence is poorly calibrated | Store it, but trust **verification status** and **ambiguity flags**, which are computed in code. |
| 4 | Separate tables for events, claims, entities, locations, timelines and topics | Premature normalization: many tables to migrate whenever the schema evolves | The **full validated JSON per (article, analysis version)** is the source of truth. **Normalized tables only where queries need them:** entities, places and their article links (for "who", "where" and the map). Claims, timeline and topics stay in JSON, indexed with GIN, and are normalized later if a real query needs it. |
| 5 | Country-specific hierarchies for every country | Not justified by the data: Morocco is the focus, and other countries appear mostly by name | Morocco gets full region / province-prefecture / commune resolution. Other countries get country plus first-level division from the same gazetteer. |
| 6 | Southern provinces not addressed | GeoNames' Morocco file lacks [southern city], Agadir and [southern city] (89 articles mention them) | Section 5.3: complete map of Morocco; owner chooses A or B |
| 7 | "Remove the losing model from dependencies" | Models are not code dependencies; they live in LM Studio's storage | The code knows one model through `LLM_MODEL`. Deleting the other model's files is the owner's choice, in LM Studio. |
| 8 | Human evaluation of about 30 articles against the full schema | That is realistically **5–8 hours** of careful work, not 1 | 30 articles across categories, evaluated on **core fields first**, plus a smaller extended-field check. The time is stated upfront. |
| 9 | An "editable evaluation file containing the article text" | The repo is **public**, so committed evaluation files would publish article text | Evaluation files live **outside the repo** (`~/news-eval/`). Only aggregate scores and the decision record are committed. |
| 10 | "Bounded concurrency" | LM Studio serves one loaded model on a 16 GB Mac, so parallel requests mostly queue | Concurrency 1 by default, configurable. Resumable batch runs instead. |
| 11 | "Exact model version" | LM Studio's API returns only a model id | Record the model id plus a **fingerprint** of the local model files (hash of the config and weight index), so a silently replaced model is detected. |

**Also added:**
- **Qwen 3.5 "thinking" mode** affects speed and is measured both on and off.
- **Prompt-injection hygiene:** article text is data. It is delimited and never followed as instructions.
- **Output size caps.**

## 1. Architecture

```
articles + article_bodies (private)
        │  eligible: has body, rights allow analysis, no analysis for current version
        ▼
news analyze ── readiness: LM Studio up? model loaded? DB migrated?
        │
        ├─ prepare: numbered paragraphs, publication date as the time reference
        ├─ LLM call(s) via OpenAI-compatible API (LM Studio, localhost only)
        │     response_format = JSON Schema (constrained decoding where supported)
        ├─ validate: Pydantic schema v1 → reject malformed or incomplete (retry once)
        ├─ verify evidence: quote ⊂ cited paragraph → verified | unverified
        ├─ normalize: entity names (e.g. "With AFP" / "with AFP"), dates, roles
        ├─ resolve places: local GeoNames gazetteer → resolved | ambiguous | unresolved
        └─ persist in one transaction: analysis JSON + entities + article_places
```

- **Module:** `app/analysis/` (client, schema, prompt, verifier, normalizer, pipeline)
  and `app/geo/` (gazetteer loader, resolver). The CLI gets `news analyze` and
  `news gazetteer load`.
- **Execution model:** a resumable, idempotent, bounded run by hand, exactly like
  `news ingest`. The advisory lock prevents overlapping runs.
- **LM Studio unavailable:** fail fast with an actionable message (exit 2), with no
  partial writes.
- **Locality:** inference happens only on localhost, and article text never leaves the
  machine. The client refuses a non-local `LLM_BASE_URL` unless explicitly overridden.

## 2. Model selection (one model in production)

- **Candidates:** Qwen3.5-9B (MLX 4-bit, 5.6 GB) and gemma-4-E4B-it (MLX 4-bit, 6.4 GB),
  both already in LM Studio.
- **Starting hypothesis:** Qwen. **Not a conclusion until measured.**
- **Procedure (once):** the same 30 articles, the same prompt and the same schema, run on
  both models. Then:
  1. **automatic measures:** JSON validity, evidence-verification rate, latency, tokens
     per second, peak memory;
  2. **human measures:** factual precision and completeness, entity accuracy, temporal
     accuracy, geographic accuracy, hallucination rate.
- **Selection rule:** first, the model with fewer hallucinations and unsupported
  claims. Then completeness. Speed only breaks ties.
- **After the evaluation:** the winner's id goes in `LLM_MODEL`, and the decision record
  (`docs/decisions/model-selection.md`: date, scores, model fingerprints) is committed.
- **Not built:** no multi-model pipeline and no comparison dashboard. The evaluation is a
  one-off script.

## 3. Analysis JSON schema v1 (Pydantic is the source of truth)

```jsonc
{
  "schema_version": "1",
  "overview": {
    "headline": "...", "summary": "...",
    "report_type": "new_event|update|reaction|investigation|background|opinion",
    "event_status": "completed|ongoing|planned|uncertain"
  },
  "what": {"main_event": "...", "secondary_events": ["..."]},
  "who": [{
    "name_as_written": "...", "normalized_name": "...",
    "type": "person|government_body|political_party|company|ngo|intl_org|group|media|other",
    "role": "...", "involvement": "central|participant|quoted|mentioned",
    "evidence": {"paragraph": 3, "quote": "..."}
  }],
  "when": {
    "publication_date": "2026-11-20",
    "event_date": {"value": "2026-11-19", "precision": "day|month|year|range|unknown",
                   "end": null, "as_written": "on Wednesday", "evidence": {"paragraph": 1, "quote": "..."}},
    "timeline": [{"date": "...", "precision": "...", "event": "...", "evidence": {...}}]
  },
  "where": [{
    "name_as_written": "...", "normalized_name": "...",
    "role": "event_location|actor_location|origin|destination|mentioned|related_event",
    "country": "MA", "admin1": "...", "admin2": "...", "admin3": "...",
    "locality": "...", "specific_place": "...",
    "ambiguous": false, "evidence": {"paragraph": 2, "quote": "..."}
  }],
  "claims": [{
    "text": "...", "kind": "fact|attributed_statement|allegation|opinion|prediction|inference",
    "attributed_to": "...", "evidence": {"paragraph": 4, "quote": "..."}, "confidence": 0.8
  }],
  "why":   [{"text": "...", "kind": "stated|attributed|interpretation", "attributed_to": null, "evidence": {...}}],
  "how":   {"description": "...", "steps": ["..."]},
  "impact":[{"area": "citizens|government|economy|public_services|international|environment|security",
             "text": "...", "certainty": "confirmed|expected|possible", "evidence": {...}}],
  "context": [{"text": "...", "evidence": {...}}],
  "next":  [{"text": "...", "date": null, "certainty": "confirmed|expected|possible", "evidence": {...}}],
  "open_questions": ["..."],
  "topics": ["..."],
  "tone": {"label": "neutral|positive|negative|critical|concerned|urgent|analytical",
           "evidence": [{"paragraph": 1, "quote": "..."}]}
}
```

**Validation rules (in code, beyond the schema):**
- Every `evidence.paragraph` exists, and its `quote` is found in that paragraph;
  otherwise the claim is `unverified`.
- `event_date` must not be after `publication_date` unless `report_type` is planned or
  `next`.
- `precision` must match the value's form; an `unknown` date has no value.
- `admin*` fields are kept as written by the model, but **only the resolver's output is
  authoritative**.
- **Caps:** at most 40 claims, 30 entities and 20 places. Quotes are at most 300
  characters.

## 4. PostgreSQL schema (migration plan)

```sql
analyses(id, article_id FK, analyzer_version, schema_version, prompt_version,
         model_id, model_fingerprint, status CHECK IN ('succeeded','invalid','failed'),
         result jsonb, error text, duration_ms, tokens_in, tokens_out,
         claims_total, claims_verified, created_at,
         UNIQUE(article_id, analyzer_version))          -- history kept per version
entities(id, type, canonical_name, UNIQUE(type, canonical_name))
entity_aliases(entity_id FK, alias, UNIQUE(alias, entity_id))
analysis_entities(analysis_id FK, entity_id FK, name_as_written, role, involvement)
geo_places(geonames_id PK, name, ascii_name, feature_class, feature_code, country,
           admin1_code, admin2_code, admin3_code,          -- as sourced, never edited
           latitude, longitude, population, source_version)  -- gazetteer, loaded locally
geo_place_names(geonames_id FK, name, lang)            -- alternate names (ar, fr, en, …)
geo_admin_names(country, level, code, name)            -- region / province / commune names
analysis_places(analysis_id FK, name_as_written, role, geonames_id FK NULL,
                resolution CHECK IN ('resolved','ambiguous','unresolved','manual'),
                candidates jsonb, note)
-- Indexes: GIN(result jsonb_path_ops); analysis_places(geonames_id); geo_place_names(lower(name))
```

- **Bodies stay in `article_bodies`;** generated data stays in `analyses`.
- **Quotes inside `result` are private text,** treated like bodies: never served.
- **`news_api` role:** may read `entities`, `analysis_places` and `geo_*`. It gets no
  access to `analyses.result` until a curated, quote-free view exists.

## 5. Geographic resolution

### 5.1 Data source (free, offline, licensed)
- **GeoNames** (CC BY 4.0, attribution required in the README):
  - `MA.txt` (plus, under option A in section 5.3, the records of three southern cities);
  - `admin1CodesASCII.txt` and `admin2Codes.txt`;
  - `alternateNamesV2` filtered to MA (Arabic, French and English names);
  - `cities15000` for the rest of the world.
- **Verified 2026-11-23:** GeoNames lists **12 Moroccan regions (the 2015 reform)**.
- **Still to verify in 9.4:** whether provinces and prefectures (admin2) and **communes
  (admin3)** are complete and current. If communes are missing, the HDX/OCHA
  administrative boundaries for Morocco are the fallback; their license must be checked
  first.
- **Loading:** `news gazetteer load` downloads, verifies and loads the files into the
  `geo_*` tables, recording `source_version` (the download date and file checksums).

### 5.2 Resolver (deterministic, no LLM)
1. Normalize names (casefold, strip accents, handle Arabic and French variants) and look
   them up in `geo_place_names`.
2. Narrow by the country and admin hints from the model, then by feature class
   (populated place or administrative area).
3. Score the matches. If the top two are close → **ambiguous**, keeping the candidates.
   If there is no match → **unresolved**.
4. Coordinates and hierarchy come **only from the gazetteer**.
5. A neighbourhood or establishment is kept as text. It is never geocoded beyond the
   locality it was matched to.
6. `manual` resolutions, for later manual correction, override automatic ones.

### 5.3 Coverage of Morocco's southern provinces (owner decision pending: A or B)

**Requirement:** a complete map of Morocco. Every place is presented as part of Morocco,
in its Moroccan region and province.

**Data fact (verified 2026-11-23):**
- GeoNames' Morocco file (`MA.txt`) does **not** contain [southern city], Agadir or [southern city].
  It does contain [southern city], [southern city] and other southern places.
- 89 collected articles mention those three cities.
- GeoNames does define all six southern provinces in its Morocco data: [southern city]
  `MA.11.321`, [southern city] `MA.11.221`, [southern city] `MA.11.121`, [southern city] `MA.11.537`,
  Aousserd `MA.12.066`, Oued Ed-Dahab `MA.12.391`.

**Option A (recommended):**
- Also import GeoNames' records for those cities and assign them **country = MA** and
  their Moroccan province.
- Nothing in the app, API, map or docs presents them differently from any other Moroccan
  place.
- The only trace is the download file name inside the loader code.

**Option B:** use `MA.txt` only. Those three cities are not resolvable, so their
articles do not appear on the map.

In both options, the LLM never decides country or hierarchy: these come from the
gazetteer data only.

## 6. Human evaluation (outside the repo)

- **Location:** `~/news-eval/<date>/`, one `article-<id>.yaml` per article. It contains
  the article id, title and URL, then for each model its output, then empty correction
  fields:
  - `missing_facts`, `wrong_facts`, `wrong_entities`, `wrong_dates`, `wrong_places`;
  - `unsupported_claims`, `evidence_ok`, and an overall score from 1 to 5.
- **The article text** is shown by a local helper command (`news eval show <id>`), not
  copied into the files.
- **Sample:** 30 articles stratified by category: Politics, International, Economy,
  Society, Sports, regional news and the southern provinces. It includes 5 deliberately hard
  cases: very long, several places, allegations, relative dates, and a mainly
  international story.
- **Scoring:** a script reads the files and computes the metrics. Only those aggregates
  are committed.
- **Effort:** about 10–15 minutes per article on core fields, so **5–8 hours** in total.

## 8. Risks

| Risk | Mitigation |
| --- | --- |
| Too slow for 1,800+ articles | Measured in 9.0. Split passes, resumable overnight runs, a core-only mode |
| Hallucinated facts or quotes | Code-verified evidence; unverified claims flagged; selection weighs hallucination first |
| Wrong event date (publication vs event) | The publication date is given as the reference; consistency rules; evaluated by humans |
| Wrong or ambiguous places | Deterministic resolver with an `ambiguous` state; no LLM coordinates; manual overrides |
| Southern cities missing from the map | Section 5.3 option A; coverage tests for [southern city], Agadir, [southern city], [southern city] and [southern city] |
| Sensitive content (allegations) | Allegations are never promoted to facts |
| Text leaking through outputs | Quotes stay private; the API serves quote-free fields only; evaluation files outside the repo |
| Gazetteer incomplete for communes | Verified in 9.4; fallback source after a license check |
| Model or LM Studio updates change results | Model fingerprint and analyzer version on every analysis; re-analysis is explicit |
| 16 GB memory pressure | One model loaded; concurrency 1; memory measured in 9.0 |

## 8b. Prompt and schema iteration log (stage 9.0/9.1, 2026-11-23)

**Method:**
- The same 10 articles every round (ids 10192, 10211, 12225, 10205, 10168, 10173, 10176,
  10215, 10280, 10170), run with `news lab` and scored with `news lab-compare`.
- Outputs go to `~/news-eval/lab/`, outside the repo.
- Each round is a single run, so differences of a few items may be run-to-run variance.

| Round | Change | Measured result | Lesson |
| --- | --- | --- | --- |
| — | Qwen thinking mode | Empty answers: LM Studio put the whole JSON in `reasoning_content` | Send `reasoning_effort: "none"`. `chat_template_kwargs` and `/no_think` had no effect |
| v1 | Full schema | 10/10 valid; 98% quotes verified **after fixing the checker** (re-quoted nested quotes) | The model extracts and quotes well, but classifies badly: it invented country and region labels, used background dates as the event date, and mislabeled report types |
| v2 | No hierarchy from the model; ISO dates; defined report types; simpler claim kinds | 16% faster; report types right | The timeline emptied; it used publication dates with fake evidence; it listed organizations as places; it renamed a place |
| v3 | Names exactly as written (code-checked); geographic places only; date quotes must contain date words; background in the timeline | 99% verified, 0 fabricated; chronology restored; undated events become "unknown" | Actor roles still off. **Model choice made on v3** (docs/decisions/model-selection.md) |
| v4 | Precise involvement and place-role definitions | Roles fixed (ambassador central, test sites as event locations) | Less complete; one answer failed because precision disagreed with the date value; origin and destination misused |
| v5 | Precision derived in code; "list every claim"; origin and destination only for movement | 241 claims, 10 fabricated quotes, 153 s per article | Over-extraction raises errors and cost. Generic phrases ("buffer zone") listed as places |
| **v6 (adopted)** | At most 15 claims; proper place names only; 4 place roles; whoever performs the headline action is central | 10/10 valid, **99%** verified, ~13 claims per article, 106 s per article | Roles right. Residual non-places and duplicates are handled by **code cleanup** and the gazetteer, not more prompt rules |
| v6 repeat | Same prompt, second run (variance) | Event date same in 10/10, report type 9/10, central actors 9/10, event locations 7/10 | **Stable.** The cleanup review found and fixed 2 cleanup bugs (listed provinces, report publications) |

**Principles that emerged:**
1. **Ask the model to extract, not to classify facts it cannot know.** Hierarchy,
   country and precision are computed or resolved in code.
2. **Every model output that can be checked against the article is checked in code:**
   quotes, names and date words.
3. **Redundant fields are removed rather than validated.** Two fields that must agree
   will eventually disagree.
4. **After a point, more prompt rules trade one error for another.** Deterministic code
   cleanup (`app/analysis/cleanup.py`) fixes the rest, and every correction is recorded.
5. **Judge prompts on repeated runs,** not single runs.
